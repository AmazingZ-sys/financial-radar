# 37 · X 采集随机间隔

设计日期：2026-11-05。用户要求把固定采集频率改为区间。目标是降低集中、重复请求；随机间隔不保证免于账号限制，不进行代理/账号轮换或验证码绕过。

- 管理页增加`pollIntervalMinSeconds`、`pollIntervalMaxSeconds`，整数300..86400，最小值不得大于最大值。新配置默认600..1200秒。旧存储仅有`pollIntervalSeconds`时，以旧值为最小、旧值1.5倍（上限86400）为最大；不在读取时改写旧记录。旧PATCH单值同样转换，旧值只作兼容，不作为后台固定调度依据。部分更新保留另一端，合并后验证区间。
- 每次实际采集器请求前在PostgreSQL同一配置锁内校验并预留调用：加密凭据与配置仍有效、每日额度可用、当前已到允许请求时间。使用服务器随机整数，在闭区间内抽取下一次间隔，持久化到`system_settings/x:poll-state`：`lastRequestAt`、`nextRequestAt`、`lastDelaySeconds`。API连接测试同样遵守间隔、计数，不绕过限制。Fixture不建立真实请求预留。
- 配置热更新影响下一次预留的区间；已有下一次请求时刻保留，保存配置、重启或Redis丢失不会反复抽签或缩短等待。限流时将共享下一次时刻推迟到当前预留时间与供应商冷却时间中的较晚者；失败不立即重试。界面显示区间、下一次允许请求时间和最近抽取间隔。
- X停止使用BullMQ固定周期scheduler。每15秒协调器从PostgreSQL读取允许时刻，投递有稳定时间标识的单次延迟任务；Redis仅承载调度、事实仍在PostgreSQL。首次启用或没有预留时允许一次采集；实际请求开始时先持久化下一次时刻，即使中途崩溃也不会立即补打一轮。已有旧scheduler移除；遗留任务在执行/最终请求预留前复查，共享锁确保多实例仅一次请求。
- 关闭来源、凭据失效或每日额度为0不调度；每日额度耗尽等待UTC次日。固定频率的其他来源不改变。`data_sources.next_poll_at`作为来源状态镜像，不作为X真实请求门禁的独立真相。
- X 启停与随机区间统一在系统管理保存；来源页仅提供管理链接，通用来源 PATCH 拒绝修改 X 的启用状态或周期，避免来源表与管理配置相互覆盖。Worker 初始化保留 X 的随机区间说明。
- 验证覆盖上下界、反转/非整数拒绝、旧配置迁移、部分更新、不同随机样本、持久重启/重复任务、并发预留、手动测试与采集共享间隔、429冷却优先、额度与Fixture、管理页保存重载/显示。运行约定检查并记录acceptance；不使用真实X登录态。
