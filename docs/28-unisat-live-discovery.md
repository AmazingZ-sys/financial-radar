# 28 · UniSat 近期部署监控与去重

设计日期：2026-11-04。修复状态索引把多年以前的部署反复作为新事件采集的问题；本设计先于实现。

## 监控范围

Live 新部署发现仅接纳链上部署时间位于采集时刻之前 7 天内的状态；部署时间未知、无效、未来或超过窗口的记录不进入事件、项目与新部署信号链路。已保存的历史事实保留，不自动删除或改写时间。此来源不承担旧代币的全量持仓/交易监控。

官方 [BRC-20 OpenAPI](https://raw.githubusercontent.com/unisat-wallet/unisat-dev-docs/master/open-api/swagger-source/brc20-indexer.yaml) 公开 `start`、`limit`、`sort=deploy`、`complete=yes/no` 与返回 `total`，没有声明升降序参数。每个完成状态分组读取首部及必要的尾部，合并 inscription ID，按有效部署时间选最新 50 条未完成、20 条已完成候选，再应用 7 天窗口。最多 4 次请求，每秒至多 1 次；供应商数据变动导致的分页边界漂移及窗口外覆盖仍是明确限制。缺失 total 时只保留首部覆盖，不能声称全量。

## 状态与身份

PostgreSQL checkpoint 保存版本化的最近状态指纹及批次序号。指纹按实际使用的代币字段计算，十进制规范化，不包含本轮观察时间、索引高度或无关供应商元数据。状态不变时无新 raw/event/metric；变化或新候选才记录快照，状态 A→B→A 也应保留。状态缓存最多 2,000 项，按最近出现时间淘汰并排除超过部署窗口的项；超出缓存覆盖的重新进入可能再观察一次，不能承诺全链 exactly-once。

快照 ID 由 checkpoint 中的下一批次序号、inscription ID 与状态指纹组成，不包含本轮采集时间。保存部分事实后失败时，相同 checkpoint 和响应产生相同 ID；只有整轮成功才提交新的 checkpoint，沿用 Worker 现有事务和源级锁。重试遇到已保存的原始 ID 时，使用数据库原始 payload 和发布时间重新标准化，保持观察时刻与证据一致。旧版 checkpoint 自动建立新基线，不能把旧的 checkedAt 当成部署时间。

新增向前兼容的 `source_pending_batches` 表，在处理首项前保存本轮响应及下一 checkpoint。失败/重启先重放该批次，再于后续轮询读取供应商新响应，避免部分写入 B 后因上游回到 A 而被旧 checkpoint 错误抑制。整轮成功时原子提交 checkpoint 并移除已完成批次；不清理历史事实，不依赖 Redis。

变化采样不能直接沿用稀疏快照的时间间隔估算铸造加速。每个变化快照附带前一状态最后一次确认时间及其指纹，checkpoint 中的不变轮询更新时间只用于此证据基线；历史检测校验相邻状态指纹后，以实际确认的区间计算速率，缺失或不兼容证据时不计算加速。原始快照包含基线时间与指纹，检测结论可追溯。

标题采用「BRC-20 状态更新」。`eventOccurredAt` 保持真实部署时间，`sourcePublishedAt` 保持未知，首次发现/采集时间来自实际处理链路；观察时间参与指标历史而不伪装成部署时间。没有来源新数据时继续按计划健康轮询，零条新增是正常结果。

## 验收

单元覆盖首尾页的升降序、古老/未知/无效/未来部署、窗口边界、相同状态、数值格式变化、真实变化、状态回归、重启恢复、失败与确定性重试。真实 PostgreSQL Fixture 集成验证连续轮询、重启及部分处理失败后的持久 checkpoint、事实计数和时间字段；合成响应必须显式标记 fixture。生产凭据实采、旧数据清理与发布分开记录。
