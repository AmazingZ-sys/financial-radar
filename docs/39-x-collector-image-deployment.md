# 39 · X 采集器镜像与一键部署

设计日期：2026-11-06。Python 采集器已有 Dockerfile，但旧生产流程只发布、拉取及启动 API/Worker，仍需服务器本地构建。将采集器纳入同一 Release，服务器无需安装 Python 或运行 pip。

- 发布增加 `ghcr.io/<owner>/financial-radar/x-collector:vX.Y.Z`，与 API/Worker 使用同一 commit、OCI 版本标签及不可变 digest，三个收据全部成功后才上传 image-manifest。生产 Compose 使用预构建镜像，不使用本地 build 或额外 profile。
- 服务只在 Docker 网络监听 `8080`，API/Worker 使用 `http://x-collector:8080`。不添加宿主端口，不占用 `8888`，不要求开放防火墙或新增 Nginx 站点。本地开发仍可使用回环 `18080:8080`。
- 部署脚本校验三镜像来源、版本、commit、digest，启动并等待采集器健康后再替换 API/Worker。无共享密钥时自动生成32字节随机值，保存在服务器 `.deploy/x-collector.secret`（0600）；已有环境配置优先，不打印、不提交、不写入镜像。三个容器使用同一密钥。登录态继续由管理页填写并在 PostgreSQL 加密保存，部署不代填真实 X 登录态。
- 兼容历史仅含 API/Worker 的清单与三行状态；新状态在第四行保存采集器 digest。历史版本不自动构建或猜测采集器镜像。回滚恢复所选版本的镜像集；回滚历史双镜像版本时保留已有采集器容器，避免影响历史手动接入。备份/迁移失败不替换应用，数据库与卷保持现有恢复策略。
- 回滚历史双镜像版本仍向 API/Worker 注入已生成的共享密钥。旧版手工启动的采集器没有受验证 digest 记录，无法据历史应用状态还原其旧镜像；保留容器不等于验证其历史版本。
- 验收覆盖三镜像及历史清单、不可变状态、采集器健康失败、版本标签不一致、缺失或非法收据、共享密钥生成/复用/脱敏、无宿主端口，以及真实 Docker 内网 API/Worker 到采集器健康/鉴权连通。所有 X 测试使用明确的本地合成请求，不访问真实 X；镜像发布、服务器部署和真实登录态采集需分别记录实际证据。
